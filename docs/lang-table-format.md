# LangPackageTableCnData.bytes 형식과 업데이트 후 복구

2026-09 기준 실측. 한패 저장소(nemasdf/haguel-baefo) 버전 4개로 확인했다.

## 형식

```
[u32 LE headerLen][header (protobuf)][body (protobuf)]

header:
  1: varint = 10          # 청크 크기 (Id 10개 단위)
  2: varint = 1
  3: repeated Chunk       # 청크 번호 내림차순으로 기록됨
     Chunk { 1: chunkId (= Id / 10)
             2: Loc { 1: offset (body 시작 기준), 2: size (청크에 속한 레코드 바이트 합) } }

body:
  1: repeated TextMap     # Id 오름차순
     TextMap { 1: int64 Id, 2: string Content (UTF-8) }
```

- proto3 규칙대로 0 값과 빈 문자열 필드는 생략된다 (첫 청크의 offset 0 등).
- 게임은 청크 색인으로 필요한 10개 단위만 읽는다. 내용을 바꾸면 **색인을 반드시 다시 계산**해야 한다.
- 파싱 → 재작성 결과가 원본과 바이트 단위로 같음을 확인했다 (49.7만 항목, 45.4만 항목 두 버전).

## 게임 업데이트가 한패를 깨는 이유

Id 는 1001 부터 연속이지만 **게임 업데이트마다 전부 다시 매겨진다.** 다른 게임 데이터가 텍스트를 Id 로 참조하므로, 옛 한패를 새 버전에 넣으면 문장이 엉뚱한 자리에 나온다.

| 한패 버전 비교 | 같은 Id·같은 문장 | 항목 수 |
|---|---|---|
| 08-04 → 08-27 | 33 | 454,043 → 464,654 |
| 08-27 → 09-08 | 42 | 464,654 → 477,267 |
| 09-08 → 09-27 | 260 | 477,267 → 497,166 |

연속된 Id 가 평균 15개 안팎의 묶음으로 함께 움직이고, 묶음 순서가 섞인다. Id 로는 옮길 수 없고 **중국어 원문으로 매칭**해야 한다.

## 앱 내 복구 설계

**대상은 중섭(官服·빌리빌리·QQ)뿐이다.** 공식 원문을 읽는 곳과 복구본을 쓰는 곳 모두 중섭으로 확인된 설치에 한정한다. 안드로이드는 패키지 허용 목록(`com.Sunborn.SnqxExilium`, `.bilibili`, `.qq`), PC는 `CnServerCheck` 를 통과한 폴더만 쓴다.

1. **공식 원문 보관**: 게임 폴더의 파일이 공식본(한글 없음)일 때마다 보관한다. 지문(항목 수 + 비언어 항목 해시)으로 버전을 구분한다.
2. **번역 메모리**: 한패와 지문이 같은 공식본이 있으면 같은 Id 끼리 짝지어 `중국어 원문 → 한국어` 를 만든다. 버전이 바뀌어도 누적한다.
3. **감지**: 게임 업데이트로 게임 폴더에 새 공식본이 들어오고, 그 지문이 최신 한패와 다르면 "한패가 이 버전과 맞지 않음".
4. **재파싱·복구**: 새 공식본의 모든 항목을 원문으로 번역 메모리에서 찾아 한국어로 바꾸고, 없는 문장(새 콘텐츠)은 중국어로 둔 뒤 색인을 다시 계산해 적용한다.
5. **정식 한패 복귀**: 한패 저장소에 새 버전이 올라오고 지문이 게임과 맞으면 정식 한패로 교체한다.

같은 원문이 여러 번역으로 쓰인 경우는 옛 Id 주변 묶음의 대응 관계(묶음 단위 이동)로 고른다.

### 엔진 (`app/src/main/java/com/hoho/snqxkr/langtable`)

| 파일 | 역할 |
|---|---|
| `LangTable` | 읽기/쓰기, 청크 색인 재계산, 버전 지문(`layoutKey`: Id 집합 해시) |
| `Texts` | 문장 목록. 문장을 복사하지 않고 파일 안의 자리(버퍼 번호·시작·길이)만 든다 |
| `TranslationMemory` | 원문 64비트 해시 → 번역. 같은 버전 공식본+한패로 만들고, 버전끼리 합치고(줄마다 세대), 최대 500MB 로 자르고, 파일로 저장 |
| `PatchRepair` | 1단계: 새 공식본을 번역 메모리로 한국어화. 2단계: 옛 한패의 번역을 새 Id 자리로 옮김. 통계(번역/옛 한패에서 옮김/중국어로 남음). 자리 검사 |
| `Engines` | 파일 단위 엔진 (`layoutKey`, `alignment`, `buildMemory`, `repair`). Kotlin 엔진과 C++ 네이티브 엔진(`native/`, native 판에만)을 같은 모양으로 쓴다 |

같은 엔진이 세 벌 있고 결과가 바이트 단위로 같다 (번역 메모리 파일, 복구본 SHA-256, 줄 수):

| 엔진 | 쓰는 곳 | 확인 |
|---|---|---|
| Kotlin (`langtable/`) | 안드로이드 kotlin 판, native 판에서 .so 를 못 올릴 때 | `LangTableTest` |
| C# (`windows/.../Engine/`) | `SnqxKR.exe`, `SnqxKR-native.exe` 에서 DLL 을 못 올릴 때 | `SnqxKR.EngineCheck` |
| C++ (`native/`) | `libsnqx.so` (안드로이드 native 판, arm64 armv8-a), `snqx.dll` (x64, `SnqxKR-native.exe` 안에 넣음) | `native/cli.cpp`, 스트레스 테스트 |

- 메모리: 세 엔진 모두 문장을 줄마다 복사하지 않고 파일 내용 안의 자리만 든다 (문자열 풀 + 위치표). 줄마다 Id 8바이트 + 시작 4 + 길이 4, 복구 결과는 어느 파일인지 1바이트를 더 든다.
  - 줄 수를 먼저 세어 배열을 딱 맞게 잡는다. 옛 한패 옮기기는 Id 를 복사하지 않고 "Id 순 다음 줄과 1 차이인지" 만 1바이트로 들고, 1단계에서 2단계용 키를 Id 순 자리에 바로 쓴다.
  - Kotlin: 파일을 메모리 매핑한다. 매핑한 파일은 Java 힙 한도에 들지 않고, 메모리가 모자라면 OS 가 내렸다가 다시 읽는다 (안드로이드가 `resources.arsc` 를 읽는 방식). 복구 한 번(옛 한패 포함)에 필요한 힙 192MB → 48MB, 속도는 같다.
  - C++: 매핑하고 작업이 끝나면 바로 푼다 (안드로이드 `mmap`, 윈도우 `MapViewOfFile`). 매핑을 못 하면 통째로 읽는다. 표의 문장 자리는 포인터 대신 `{시작, 길이}` 8바이트. 복구 중 늘어나는 익명 메모리 약 +53MB (S25).
  - C#: 매핑하지 않고 한 번에 읽는다. 윈도우는 매핑 중인 파일을 다른 프로그램(게임 업데이트)이 줄이거나 바꾸지 못하고, PC 는 메모리가 넉넉하다.
  - 매핑한 파일이 읽는 도중 잘리면 리눅스·안드로이드는 SIGBUS 로 죽는다. 앱은 엔진이 읽는 파일을 모두 임시 파일에 쓴 뒤 이름을 바꾸고 한 번에 하나씩만 돌린다. 출력이 입력과 같은 파일이면 엔진이 임시 파일로 돌린다.
- 깨진 파일: 길이 값이 음수이거나 남은 크기보다 크면 오류로 끝낸다 (읽는 위치가 뒤로 가 끝없이 돌거나 큰 배열을 잡지 않게). 번역 메모리 줄 수도 파일 크기로 확인한다. varint 는 protobuf 규칙대로 10바이트까지 (세 엔진 같음).
- 자리 검사 (`alignment`): 한패에서 번역하지 않은 줄(한글 없이 한자만)이 같은 Id 의 공식 원문과 같은 비율. 번역 수정판은 이 값을 바꾸지 않는다 (번역한 줄은 보지 않는다). 기준 90% (`MIN_ALIGNMENT`), 판단할 줄이 20줄 미만이면 판단하지 않는다. 걸린 한패는 번역 메모리에 넣지 않고, 적용은 막되 사용자가 "그래도 적용" 할 수 있다.

번역 메모리 파일 (빅엔디안, 안드로이드·윈도우 같은 형식):

```
v2: "SNQ2" u32 개수, 줄마다 { i64 원문 해시, i32 세대, i32 길이, 번역 UTF-8 }   (해시 오름차순)
v1: "SNQM" u32 개수, 줄마다 { i64 원문 해시, i32 길이, 번역 }                     (읽기만, 세대 0)
```

- 세대: 합칠 때마다 1씩 늘고, 새로 합친 한패에 있던 줄은 새 세대가 된다. 파일이 500MB 를 넘으면 세대가 낮은 줄(오래전 한패에서만 본, 게임에서 사라졌을 가능성이 큰 문장)부터 뺀다. 지금 속도(업데이트마다 1~2MB)로는 몇 년 걸린다.
- 윈도우 0.2 는 리틀엔디안 v1 을 썼다. 첫 4바이트로 가려 그대로 읽는다.

### 옛 한패 번역 옮기기 (임시 복구 2단계)

옛 한패 파일만으로는 새 버전에 맞출 수 없다. 실측 (옛 한패 → V1 공식 원문):

- 같은 문장이 Id 순으로 두 줄씩 붙어 있는 경우가 대부분이고(대사 한 줄 = Id 두 개), Id 는 4~8줄 단위로 섞인다.
- 한패는 번역하지 않은 줄(중국어 그대로·숫자·기호)이 거의 없다 (V4 한패 46.5만 줄 중 새 원문과 글자로 한 번씩만 맞는 줄 1,795줄, 0.4%).
- 그래서 V2 한패를 번역 메모리 없이 V1 원문에 맞대면 3줄 이상 이어지는 구간이 684줄뿐이고, 옮길 수 있는 한국어 줄은 0줄이다.
- 줄 길이 비율·끝 문장부호·괄호·숫자·태그 모양으로 구간을 맞대 보면 옮긴 줄의 약 70% 만 맞아 쓰지 않는다 (틀리면 대사가 엉뚱한 장면에 나온다).

그래서 번역 메모리가 기준점을 만든다. 1단계 결과(대부분 한국어)와 옛 한패를 Id 순으로 늘어놓으면 같은 문장이 연속으로 이어지는 구간이 많다.

1. 옛 줄마다 같은 문장인 새 줄 후보(16개 이하)를 찾아, 앞뒤로 같은 문장이 몇 줄 이어지는지 잰다. 3줄 이상이고 가장 긴 후보가 하나뿐일 때만 대응으로 정한다.
2. 대응된 두 줄 사이가 옛·새 양쪽 모두 끊김 없이 같은 길이면, 그 사이 줄도 같은 차이로 옮긴다 (메모리에 없던 새 번역, 한패 팀이 고친 표현).
3. 한 자리에 두 줄이 오면 버리고, 옮길 번역과 새 원문의 태그·자리표시자·숫자가 다르면 버린다 (예: 150% → 180% 로 바뀐 스킬 설명).
4. 옛 한패가 번역 메모리보다 새것일 때만 한다 (`cachedSha ≠ memoryPatchSha`). 메모리가 이미 그 한패를 담고 있으면 얻는 게 없고, 원문이 바뀐 줄에 옛 번역을 얹게 된다 (역방향 실험: V1 메모리 + V2 한패 → V4 에서 옮긴 줄이 V4 한패와 0% 일치).

| 파일 | 역할 |
|---|---|
| `PatchEngine` | 화면·백그라운드 공용. 게임 폴더 상태 판정, 공식 원본 보관, 번역 메모리 갱신, 버전 불일치 시 적용 차단, 임시 복구, 원본 복원(옛 버전 백업이면 거부), GitHub 이력으로 번역 메모리 준비 |
| `PatchCheckWorker` | WorkManager 3시간 주기. 한패 확인(모바일 데이터는 설정), 게임 폴더 확인 후 알림만 (파일은 바꾸지 않음) |
| `FileService.tableLayout` | 게임 폴더 파일의 버전 지문을 특권 프로세스에서 계산 (앱은 게임 폴더를 직접 못 읽음) |

알림은 같은 사건을 한 번만 띄운다: 한패가 풀림(게임 업데이트) / 정식 한패 나옴(임시 복구 중) / 같은 버전 번역 갱신(조용한 채널).

백그라운드 확인·알림 원칙 (배터리·백그라운드 점유 방지):

- 기본값은 꺼짐. 꺼져 있으면 예약 작업 자체가 없다. 알림 권한은 사용자가 기능을 켜는 순간에만 묻는다.
- WorkManager 주기 작업만 쓴다 (6/12/24시간, 기본 12시간, flex 1/4). 네트워크 연결 + 배터리·저장공간 부족 아님 조건. 상주 서비스·wakelock·정확한 알람 없음.
- 바뀐 게 없으면: 한패는 HEAD(0바이트), 게임 파일은 크기·수정시각만 본다 (56MB 해시·본문 읽기 생략).
- 볼 클라이언트가 없거나 알림이 전부 꺼져 있으면 Shizuku 를 깨우지 않는다. 끝나면 특권 프로세스를 내린다.
- 옛 한패 다운로드(번역 메모리 준비)는 백그라운드에서 하지 않는다. 앱을 열었을 때 번역 메모리가 없고 1.0 원본 백업이 있으면 Wi-Fi(또는 모바일 데이터 허용)에서 자동으로 한다.
- 알림 종류(풀림·정식 한패·번역 갱신)를 설정에서 따로 끄고 켜며, 채널도 나눠 시스템 설정에서도 조절된다. 번역 갱신은 기본 꺼짐.

Shizuku 는 무선 디버깅·adb(shell, uid 2000)를 기본으로 가정한다. 이 방식은 재부팅하면 꺼지므로, 백그라운드 확인 때 Shizuku 가 꺼져 있으면 게임 폴더는 건너뛰고 마지막으로 본 게임 상태로만 "정식 한패 나옴·번역 갱신"을 판단한다 ("한패가 풀림"은 Shizuku 가 켜져 있어야 알 수 있다).

기존 1.0 사용자는 처음 적용할 때 남긴 원본 백업(당시 버전 공식본)으로 번역 메모리를 준비한다. GitHub 커밋 이력에서 색인만 받아(`Range`, 1MB 안쪽) 같은 버전 한패를 찾고, 그것 하나만 전부 받는다.

### 남은 과제

- 한패와 같은 버전의 공식 원문이 한 번은 있어야 번역 메모리를 만들 수 있다. 이 앱으로 처음 적용하면(적용 전 원본 보관) 또는 1.0 원본 백업이 있으면 자동으로 생긴다. 다른 방법으로 한패를 넣어 이 앱이 원문을 본 적이 없으면, 첫 업데이트는 새 한패를 기다려야 한다 (옛 한패만으로 옮기기는 위 실측대로 불가).
- 게임 서버에서 공식 원문을 직접 받는 방법: 리소스 목록(`Version_Ex1.bin`)과 로그가 암호화돼 있어 보류.
- 번역 메모리가 옛 버전(V4)이면 그 뒤 버전에서 새로 생긴 장면(약 3만 줄)은 2단계로도 옮기지 못한다. 장면 전체가 새것이라 기준점이 없다.
